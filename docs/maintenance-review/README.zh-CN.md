# HSD CIPHER SM 项目分析与开源维护建议

本文记录原提交 `f1af537ab46215446dd04918179440a9b08b1615` 的历史状态。当前工作树已进入 2.0 修复，现有接口与验证结果以根目录 README、迁移指南和验证记录为准。附带探针会从 Git 提取该历史提交，避免把已修复代码误当作旧漏洞样本。

截至 2026 年 10 月 8 日，项目最值得投入的方向是：提供一个容易接入、行为明确、能够与其他实现互通的 Java 国密工具库，同时帮助旧使用者安全迁移。恢复维护首先要处理已经确认的 SM2 私钥泄露和密文完整性问题，再恢复构建、测试与文档，最后发展格式转换和跨语言示例。

当前版本适合研究历史实现。由于签名随机数固定、私钥被打印、解密未验证 C3，不能作为新生产系统的密码组件直接使用。SM3、SM4 部分基础运算的对照测试通过，不代表整个库具备生产使用条件。

本次基于提交 `f1af537ab46215446dd04918179440a9b08b1615`，检查了全部 10 个生产 Java 文件、3 个测试文件、POM、README、CI 和提交历史，并读取公开 issue。验证使用合成数据和临时密钥。本文与附带探针属于分析材料，生产代码及原始配置没有修改。它不构成密码产品认证，也未覆盖侧信道、硬件环境和全部恶意输入。

## 项目现状与可保留的价值

本地最后一次提交是 2020 年 1 月 7 日；生产 Java 代码最后一次变更是 2017 年 11 月 21 日。约七年的仓库维护中断，对应接近九年未调整的算法实现。

| 组成 | 当前能力 | 对使用者的实际限制 |
| --- | --- | --- |
| SM2 与 Cipher | ECC 参数、密钥生成底层对象、加解密、签名验签 | 默认测试曲线，签名及解密存在严重问题，没有便捷的标准密钥生成入口 |
| SM3 与 SM3Digest | 摘要计算、分块更新 | 输出偏移、状态复制、复用及大数据长度处理有缺陷 |
| SM4 与 SM4Utils | SM4 分组运算、ECB/CBC、填充、Base64 字符串接口 | 内部 JDK API、固定 GBK、填充校验不足、没有认证加密接口 |
| Util | 数值、字节、Hex、字符串转换 | 多套重复接口，输入检查和编码语义不一致 |
| 工程与发布 | 单模块 Maven 项目、一个 Java CI | 动态依赖、缺少明确编译配置与测试引擎、内网发布地址、没有许可证文件 |

生产代码约 2,217 行，测试代码 119 行。项目足够小，适合收敛成维护成本可控的工具库。已有的直接方法调用、独立的 SM3/SM4 核心代码、中文背景资料，都可以成为教学或迁移材料。

对新使用者而言，真正需要解决的通常是“生成什么格式的密钥”“为什么对方解不开”“签名为什么验不过”“升级依赖会不会破坏旧数据”。这些环节应该成为恢复维护后的主要产品能力。

## 优先处理的实现问题

P0 表示应在引导任何新生产接入前处理；P1 表示影响基本正确性、互通或可安装性；P2 表示提高长期可维护性。这里的优先级用于安排维护工作，不是正式 CVSS 评级。

### SM2 签名可暴露私钥

**P0，已复现。** [SM2.java 第 125 至 134 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2.java#L125-L134) 先生成随机数，随后用固定测试常量覆盖 `k`。真实签名每次使用同一个、公开可知的随机数。

按代码中的签名方程，已知一份签名 `(r,s)` 和固定 `k`，即可在可逆条件下计算 `d = (k-s) × (r+s)^(-1) mod n`。探针已经从一份合成签名恢复对应私钥，并验证恢复结果与原私钥相同。问题的严重程度高于常见的“重复两次 nonce 才能恢复私钥”，因为这里的 nonce 本身就在源码中公开。

此外，[SM2Utils.java 第 112 至 126 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2Utils.java#L112-L126) 会把私钥和待签名消息直接写到标准输出。探针捕获输出并确认存在完整私钥。

建议立即在项目首页说明受影响的签名路径，删除库中的敏感打印，并用维护中的 provider 替换签名实现。若使用者曾在真实业务中调用此版本的签名方法，应更换相关签名密钥，检查日志中的敏感信息，并评估历史签名的可信性。更换随机数不能恢复旧私钥的保密性。兼容模块也不应继续提供这种旧签名生成方式。

### SM2 解密没有验证完整性

**P0，已复现。** [SM2Utils.decrypt 第 81 至 96 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2Utils.java#L81-L96) 从 ASN.1 读取 C1 和 C2，计算了新的 C3，但没有读取密文中的 C3 并比较。

两种合成测试均被接受：改变 C3，仍返回原明文；翻转 C2 的一位，返回对应位改变的明文。后者说明调用方会收到可预测的被篡改内容。是否能进一步影响业务取决于业务如何使用解密结果，但库自身缺失完整性校验已经确认。

建议在返回明文前验证 C3，失败时统一抛出解密失败异常；使用 provider 的完整解密流程，并添加 C1、C2、C3 分别被修改的失败测试。输入还需验证 ASN.1 结构、元素数量、坐标合法性、私钥范围和尾随数据。

### SM2 默认使用历史测试曲线

**P1，代码与参数对照确认。** [SM2.java 第 19 至 37 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2.java#L19-L37) 启用的是以 `8542D69E...` 开头的测试参数，正式参数位于注释中。现代 Bouncy Castle 的 `sm2p256v1` 使用以 `FFFFFFFE...` 开头的标准参数；[OpenSSL 文档](https://docs.openssl.org/3.5/man7/EVP_PKEY-SM2/)也明确说明 SM2 曲线要求。

这是跨实现互通的重要障碍之一。只调整 C1C2C3 顺序、Base64 或 Hex 无法消除曲线差异。#8 的用户反馈与此风险一致，但现有反馈没有完整数据，不能断言曲线是该 issue 的唯一原因。

建议新接口固定使用命名曲线 `sm2p256v1`，测试参数仅留在明确标识的教学或旧数据模块。切换曲线时必须重新生成配套密钥和测试样本。旧曲线公钥不能只改一个 OID 或文件包装就变成标准曲线公钥。

### SM2 输入与验签范围处理不完整

**P1，部分已复现。** [SM2Utils.sign 第 112 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2Utils.java#L112) 使用有符号 `new BigInteger(privateKey)`，而解密采用无符号构造方式。合法的 32 字节私钥如果最高位为 1，会被签名路径解析为负数。探针对当前曲线范围内的此类私钥得到 `The multiplicator cannot be negative`。

[sm2Verify 第 159 至 179 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM2.java#L159-L179) 没有先检查 `1 <= r,s < n`。探针把一个有效签名中的 `s` 改为 `s+n`，验签仍然成功。这证明范围校验缺失，不等同于已经证明可伪造任意消息签名。

建议统一无符号密钥解析，按具体操作校验私钥范围，在解析边界限制输入长度、ASN.1 类型和签名参数范围。非法签名应稳定返回 false 或文档约定的解析异常，不能随机表现为类型转换、下标或曲线运算异常。

### SM3 的摘要接口存在状态错误

**P1，已复现。** 普通一次性摘要有通过的对照样本，但下列接口行为错误会影响封装、缓存、流式摘要和大文件用户。

| 问题 | 代码位置 | 验证结果 | 建议 |
| --- | --- | --- | --- |
| 忽略 `outOff` | `SM3Digest.java:44–47` | 请求从偏移 8 写入，实际从 0 写入 | 正确使用偏移并检查输出容量 |
| 复制对象丢失 `cntBlock` | `SM3Digest.java:30–35` | 输入 100 字节后复制，两份摘要结果不同 | 复制完整状态，或使用 provider 的状态复制接口 |
| `doFinal` 后没有自动 reset | `SM3Digest.java:110–121` | 同一对象再次计算 abc，与新对象结果不同 | 定义生命周期；建议与 provider 保持一致，完成后重置 |
| 长度计算先发生 int 溢出 | `SM3.java:271` | 模拟 256 MiB 输入，长度字段为 `FFFFFFFF80000000` | 用 long 保存并计算累计字节数和位数 |

256 MiB 的正确位长度字段是 `0000000080000000`。这里通过调用公开 padding 方法验证溢出路径，没有实际分配或处理完整 256 MiB 数据；完整大文件摘要仍需在修复后的回归测试中覆盖。

新的工具库建议直接使用维护中的 SM3 实现，对外提供 `digest(byte[])` 和 `digest(InputStream)`。历史实现可以保留为教学材料，不应继续承担生产摘要核心的维护责任。

### SM4 解密接受非法填充和截断输入

**P1，已复现。** [SM4.java 第 177 至 200 行](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM4.java#L177-L200) 仅根据最后一个字节删除填充，没有验证 PKCS#7 所要求的填充长度范围和全部填充字节。

探针确认：以 `01 02` 结尾的不合法填充被当作长度 2 接受；最后一字节为 0 也被接受。关闭填充时，15 字节密文被补零读成一个分组并解出 16 字节，而没有拒绝非完整分组。

建议 ECB/CBC 解密严格要求输入长度为 16 的倍数，并完整验证填充。新高层接口优先提供带认证的模式；ECB/CBC 只在协议明确要求时显式选用。当前库没有远程服务，因此本次没有证明 padding oracle 攻击；不能把不完整填充校验直接等同于远程漏洞。

### SM4 字符串封装导致兼容性与数据损失

**P1，已复现。** [SM4Utils.java](https://github.com/gotoworld/hsd-cipher-sm/blob/f1af537ab46215446dd04918179440a9b08b1615/src/main/java/com/heshidai/security/cipher/SM4Utils.java) 将明文固定编码为 GBK，密钥与 IV 却使用平台默认字符集。探针输入 `hello🙂`，加密再解密后无法恢复原文。底层 CBC 还会覆盖调用方传入的 IV 数组，重复使用同一个数组会改变后续行为。

建议密码接口以 `byte[]` 为基础，字符串接口默认 UTF-8，并允许显式指定字符集；密钥采用明确的原始字节、Hex 或 Key 对象接口。旧 GBK 数据的兼容解密应保留显式选择，不能悄悄改字符集。CBC 内部复制 IV，避免修改调用方输入。对外避免共享可变的 `SM4Utils` 配置对象。

### Hex 输入可能被悄悄改变

**P1，已复现。** `Util.hexStringToBytes` 对奇数长度向下取整，对非法字符使用 `-1` 继续运算。探针中 `ABC` 被截成一个字节，`GG` 被接受。项目另有 `decodeHex` 和 `hexToByte`，三者校验行为不一致。

建议收敛为一套严格 Hex 编解码：奇数长度和非 Hex 字符必须拒绝，空值行为明确。修复时尤其要考虑使用者的密钥输入，不能用宽松容错掩盖错误配置。

## 构建与开源交付的问题

### 原始项目在当前环境无法完成构建

使用 Maven 3.8.4 和隔离的临时依赖缓存验证，结果如下。

| 验证 | 结果 | 解释 |
| --- | --- | --- |
| 原 POM，JDK 17 | 失败 | 默认 Compiler 3.1 使用 source/target 1.5，当前 JDK 已不支持 |
| JDK 17，直接 javac 生产源码 | 失败，6 个错误 | `sun.misc.BASE64Encoder/Decoder` 不存在；修复 source/target 仍不足以构建 |
| 原 POM，JDK 8 | 测试编译失败 | `RELEASE` 解析到 JUnit API 6.1.3，class 61 与 JDK 8 的 class 52 不兼容 |
| 临时副本仅固定 JUnit API 5.10.3，JDK 8 | 3 个测试运行并通过 | 旧 Surefire 2.12.4 使用 JUnit3 provider，现有 test 前缀方法仍被发现 |
| 替换为 BC 1.86 编译 SM2 相关源码 | 失败 | DERInteger、DERObject、DEROutputStream 和 ECC 构造接口存在不兼容变化 |

因此，“只升级 BC 版本”或者“只换成 Java 17”都不是完整修复方案。POM 应固定编译器、测试框架和插件版本，使用标准 `java.util.Base64`，正确配置 JUnit Platform 与测试引擎。

应特别注意：不能声称旧测试完全没有运行。临时固定兼容 JUnit 后，三个方法确实运行了。但源码中没有任何结果断言；错误的摘要、false 验签或 SM4Utils 吞掉异常返回 null，都可能只打印到控制台，仍让构建显示成功。方法名碰巧符合旧 provider 发现规则，也不代表已经正确配置 JUnit Jupiter。

### 依赖冲突需要明确支持策略

当前依赖是 `bcprov-jdk16:1.46`。现代系列的 artifactId 不同，例如 `bcprov-jdk18on`；Maven 不会把不同 artifactId 自动当作同一个依赖版本去重，但它们可能包含同名 BC 类。两套系列同时进入应用会带来类路径行为不确定的问题。

新库应选择一个明确的 BC 系列，提供 dependency tree 排查指南；涉及 `bcpkix`、`bcutil` 时统一版本系列。对外 API 尽量不暴露 BC 的内部曲线对象和 ASN.1 类型，减少调用方对 provider 版本的耦合。默认不做全局 `Security.addProvider` 副作用，优先使用明确的 provider 实例或 lightweight API。

[BC 官方下载页](https://www.bouncycastle.org/download/bouncy-castle-java/)在本次查询时列出 1.86。本次对照也使用该版本。正式发布前应重新确认维护状态、发布说明及支持 JDK，不应把这份报告里的版本号当作永久升级目标。

### 发布与许可证尚未形成外部使用闭环

POM 只有 `1.0-SNAPSHOT`，缺少许可证、SCM、项目说明等完整发布元数据；`distributionManagement` 指向一个 HTTP 私网 Nexus。这个地址用于发布，不是用户普通构建时的依赖仓库；它的主要问题是外部贡献者无法复用原发布流程。

建议清理历史内网发布配置，建立明确的版本标签、变更记录、源码包与 Javadoc 包，再通过维护者控制的标准发布渠道交付。不要在验证真实发布前把 Maven Central 坐标写成可用的安装方式。

仓库没有 LICENSE，README 也未声明许可证。对商业团队和其他开源项目，这会直接阻碍复用决策。[GitHub 的许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)指出，公开仓库本身不能替代授权许可。维护者需要确认代码来源和授权权属，再选择适合的许可证并补充来源说明。项目使用公司命名空间，个人能够访问或维护仓库并不自动证明其拥有全部授权权利；这是待确认事项，不能由本次分析代为认定。

## 建议的项目定位与接口设计

### 选择适合个人维护的范围

| 方向 | 使用者得到什么 | 持续维护成本 | 建议 |
| --- | --- | --- | --- |
| 算法学习仓库 | 可阅读实现、向量、中间计算解释 | 较低，但必须标识不适合生产的历史路径 | 如果无法持续维护，明确转为教学项目，并提供迁移指引 |
| 基于维护中 provider 的接入与互通工具库 | 稳定接口、格式转换、可运行样例、旧数据迁移 | 可控制，重点是契约和测试 | **推荐主方向** |
| 自行维护完整密码实现 | 自主算法内核及优化 | 高，需要长期专业评审与验证 | 现有资源和代码状态下不建议作为主线 |

推荐主方向的区分度应来自“让用户少踩坑”：清楚的参数默认值、错误提示、跨语言样本、依赖兼容与迁移保障。BC 已经提供 SM2、SM3、SM4 能力；项目应把精力投入上层接入体验。可参考 [BC 的 SM2Engine](https://downloads.bouncycastle.org/java/docs/bcprov-jdk18on-javadoc/org/bouncycastle/crypto/engines/SM2Engine.html) 和 [SM2Signer 实现](https://github.com/bcgit/bc-java/blob/main/core/src/main/java/org/bouncycastle/crypto/signers/SM2Signer.java)，但封装仍要独立验证。

### 优先交付六类使用者能力

| 能力 | 使用者场景 | 应明确的契约 |
| --- | --- | --- |
| 密钥生成与导入导出 | 首次接入、系统间交换密钥 | 标准曲线；raw、SPKI、PKCS#8、PEM/DER 的区别 |
| SM2 加解密 | Java 与其他语言或设备互通 | DER 与 raw 的区别，C1C3C2/C1C2C3，C1 的 04 前缀，完整性失败行为 |
| SM2 签名验签 | 接口验签、文件或消息签名 | userId、ZA、消息摘要边界，DER 与固定宽度 r||s |
| SM3 摘要与 HMAC | 文件摘要、带密钥消息认证 | 流式处理、生命周期；普通 SM3 摘要不能代替 MAC |
| SM4 认证加密 | 新应用保护数据 | nonce、tag、AAD、封装版本和密钥标识 |
| 历史数据兼容 | 从旧版本迁移 | 显式旧曲线、GBK、旧 DER 和模式选择，不自动猜测 |

第一版可以先完成密钥、SM2、SM3 和明确的 SM4 兼容接口；HMAC、认证加密应在测试与协议约定完善后交付，避免一次扩展过多功能。

### 密码参数与数据编码必须分开表达

当前 `hexString` 同时决定密钥与 IV 的解析方式，明文采用另一种隐含编码。新 API 应将密码参数、文本编码、密钥文件格式和密文传输编码分别表达。

| 项目 | 建议的新接口行为 | 兼容行为 |
| --- | --- | --- |
| 曲线 | 固定 sm2p256v1 | 旧测试曲线只能显式选择 |
| 明文 | byte[]；文本便捷接口使用 UTF-8 | 明确指定 GBK |
| SM2 密文 | 用枚举明确 DER、RAW_C1C3C2、RAW_C1C2C3 | 保留旧 DER 解码入口 |
| SM2 公钥 | raw 未压缩点与 SPKI 分别导入 | 标识旧曲线，不能只按长度猜测 |
| SM2 私钥 | raw 无符号标量与 PKCS#8 分别导入 | 输入范围校验一致 |
| 签名 | DER 与 PLAIN_RS 分别选择 | 固定宽度 32 字节 r 和 32 字节 s |
| userId | 在签名配置中明确、可查询 | 不能静默更改已有协议的 ID |
| 解密失败 | 不返回部分明文，统一失败语义 | 对真实历史数据验证 C3，不保留忽略 C3 的默认行为 |
| 无效参数 | 可定位的参数异常 | 不吞异常再返回 null |

对于一般 SM2 接入，可记录常见 userId `1234567812345678`，同时要求与对端协议核对。[OpenSSL](https://docs.openssl.org/3.5/man7/EVP_PKEY-SM2/)明确需要 distinguishing ID；不同应用协议可能采用不同值，不能把一个常见值当作所有场景通用值。

可以定义内部已知、可验证的模式组合，而不开放任意“关闭校验”“关闭 ZA”“指定固定 nonce”的生产开关。接收预计算摘要的低层接口应另行命名并明确输入是什么，使硬件对接不会意外计算两次 SM3。

### 新数据加密应支持认证模式

当前 SM4 提供的 ECB/CBC 没有消息认证能力。新增高层接口可以优先支持经 provider 实现的 SM4-GCM；96 位 nonce、128 位 tag 可作为一个明确的协议配置起点，但需与对端实际支持情况核对，并保证同一密钥下 nonce 不重复。

[RFC 8998 的 SM4-GCM 定义](https://www.rfc-editor.org/rfc/rfc8998.html#section-3.5)可以作为参数参考。它是 TLS 1.3 场景下的 informational RFC，并不自动成为本项目文件或业务消息封装的协议，也不说明本项目获得任何认证。

若交付高层加密数据封装，应包含版本、算法配置、keyId、nonce 和 tag，并将需要防止篡改的元数据纳入 AAD；密钥本身不放入封装。已有 CBC 对接按对端协议处理认证，不能擅自改变线上报文。ECB 可以保留为显式兼容接口，但不作为首页新手示例。

## 互通与旧数据迁移应成为主要特色

### 为互通提供可复制的证据

先选择一个外部实现建立双向测试，再扩大范围。优先 BC 与 OpenSSL，然后根据用户反馈加入 Go 或 JavaScript。[sm-crypto 的官方仓库](https://github.com/JuneAndGreen/sm-crypto)明确暴露 C1C3C2/C1C2C3、DER 签名和 userId 等选项，适合作为前后端互通测试候选，不能仅凭文档声明本项目已与其兼容。

每个互通样例应给出固定的非生产测试密钥、消息原始字节、曲线、userId、密文/签名格式、字符集、传输编码、依赖版本及运行命令。测试双向加解密、双向签名验签以及篡改拒绝。随机签名和加密应验证结果可互操作；固定结果向量需要受控测试随机数，只能用于测试。

排查指南按顺序检查：曲线、密钥类型、原始字节、密文格式、C1 前缀、签名格式、userId、摘要边界。这个指南比“都是 SM2，为什么不通”的零散回答更容易让用户自行解决问题。

### 旧版本迁移需要显式识别格式

旧版本的密文没有项目版本和曲线标识，不能可靠地从外观自动判断配置。迁移应由使用者先确认来源系统和历史配置，再选择显式 profile。

| 旧内容 | 处理方法 | 必须保留的限制 |
| --- | --- | --- |
| 旧测试曲线下的 SM2 密文 | 使用隔离兼容解码器和旧私钥，验证 C3 后解密，再用新标准曲线密钥加密 | 无法通过包装转换把旧曲线密文变成新曲线密文 |
| 旧 SM2 签名 | 仅保留明确标识的历史验证与取证能力 | 固定 nonce 导致的可信性问题不会被格式转换修复；不继续生成旧签名 |
| 旧 GBK 的 SM4 数据 | 按旧模式、填充、密钥、IV 解密，明确文本按 GBK 解释，再按目标协议重加密 | 不可逆的字符替换无法通过升级恢复 |
| 历史无认证 CBC 数据 | 在来源可确认的迁移流程中处理，并记录校验策略 | 解密成功不能证明历史内容没有被篡改 |
| 旧长文件 SM3 摘要 | 用新实现重新计算并核对来源 | 新旧结果变化可能来自旧长度计算错误，不能盲目认定文件损坏 |

建议采用“读取旧数据、写入新格式”的过渡方式：备份原数据，分批转换，核对数量与业务内容，保留失败清单，再停用旧写入。迁移日志只记录记录标识、配置和结果，避免输出密钥或明文。

如果旧签名私钥还被其他用途复用，需要一并评估那些用途并轮换相应密钥。对源自不可信位置的旧密文，不能通过放宽完整性校验追求迁移成功率。

兼容代码应放在清晰隔离的包或可选 artifact 中。若同一模块就能清楚管理，也不必立即拆成多个 Maven 子模块；先用稳定的包边界降低个人维护负担。

## 面向使用者的文档与测试交付

### README 应帮助首次使用者完成任务

首页顺序建议为：当前维护状态与已知问题、适用范围、安装与 JDK 要求、五分钟快速开始、格式与参数表、互通示例、旧版本迁移、故障排查、贡献和许可证。算法发展背景及历史 PDF 可以移到参考资料。

快速开始至少包含：生成密钥、SM2 加解密、SM2 签名验签、SM3 摘要、SM4 高层加密。所有示例应来自持续测试的实际代码，不能只给无法运行的伪代码或历史固定业务密钥。

README 中“密钥长度和分组长度均为 128 位”的总述应修正：SM4 是 128 位密钥与分组；SM2 使用 256 位曲线；SM3 输出 256 位摘要。避免没有条件的“比 RSA 更快”等概括；性能结论需要算法操作、硬件、实现及参数一致的基准。旧行业数字也不应继续作为当前事实陈述。

### 发布前应具备的测试证据

| 测试类别 | 核心内容 | 能为使用者保证什么 |
| --- | --- | --- |
| 标准向量 | SM2 标准曲线的签名、加密；SM3 空输入与边界；SM4 单分组及重复运算 | 基础算法符合固定参考样本 |
| 差分测试 | 不同长度、随机字节、流式分块，与维护中的实现比较 | 避免只验证同一错误实现的自洽性 |
| 互通测试 | 与独立实现双向加解密和签名验签 | 真实数据交换可用 |
| 拒绝测试 | 篡改 C1/C2/C3/tag、错密钥、错 userId、非法签名范围、截断 DER/分组和填充 | 错误输入不会被当作可信结果 |
| 接口行为 | 高位私钥、输出偏移、摘要 reset/copy、Unicode、IV 不变、异常语义 | 封装行为稳定 |
| 历史回归 | 保存明确来源的旧曲线、GBK、旧 DER 样本 | 升级不会悄悄丢失可支持的旧数据 |
| 构建与依赖 | 支持 JDK 的矩阵、单一 BC 系列、外部最小消费者项目 | 使用者能安装、编译并调用公开接口 |

本次 12 组 SM3 摘要、6 种分块方式、SM4 标准向量和 64 组随机分组提供的是有限样本证据。尚未完成真实跨语言端到端测试、标准 SM2 的新实现验证或大规模恶意输入测试，不能在新 README 中提前声明这些能力已经通过。

CI 应在 push 和 PR 运行，明确固定工具版本并配置 Jupiter 引擎，确保没有测试时失败。可以保留 Java 8 字节码兼容，以减少现有用户升级成本，并测试 8、17、21 及明确承诺的其他 JDK；这是维护策略建议，需要结合 provider 的正式支持范围和实际成本决定。

测试数量不是主要目标。发布门槛应是关键向量、篡改拒绝、互通和迁移场景均有实际断言。对签名随机性，可以增加重复签名检查作为辅助回归，但不能仅凭“每次签名不同”证明随机源安全。

## 建议的实施顺序与验收标准

以下按个人维护者可分别完成的成果划分。阶段顺序反映依赖关系，不代表固定工期承诺。

| 阶段 | 具体成果 | 使用者价值 | 验收标准 |
| --- | --- | --- | --- |
| P0 保护已有用户 | 整理并公布明确的受影响路径与升级/密钥轮换说明；移除敏感打印；修复签名随机数和解密 C3 | 减少继续误用与已有暴露 | 固定 nonce 路径不存在；日志无私钥/明文；篡改被拒绝；警示与修复版本可对应 |
| P1 恢复可信构建 | 固定依赖与插件，标准 Base64，正确测试引擎，加入关键断言 | 新用户可构建，贡献者可验证 | 干净环境中支持 JDK 构建成功；测试报告与断言可查 |
| P1 建立标准 API | 标准曲线、密钥生成、byte[] 接口、严格编码与失败语义 | 完成可用的接入闭环 | 最小消费者项目无需了解 BC 内部类即可完成主要操作 |
| P1 保护迁移 | 旧 profile、历史样本、迁移指南、轮换说明 | 原使用者能够升级 | 已声明支持的旧样本可读取；拒绝坏数据；新写入采用明确新格式 |
| P1 提供互通成果 | 与一个独立实现的双向测试及问题排查说明 | 降低系统对接成本 | 同一组 fixtures 在双方通过，错误格式明确失败 |
| P2 正式开源发布 | 确认授权来源、许可证、版本标签、发布元数据、CHANGELOG、SECURITY、CONTRIBUTING | 商业和开源用户能放心评估和复用 | 许可证与权属事项明确；已发布版本可安装且可追溯 |
| P2 按需求扩展 | HMAC-SM3、SM4 认证加密、更多密钥格式、更多语言样例 | 扩大覆盖场景 | 每个能力有明确需求、契约、独立验证和维护责任 |

许可证与权属确认可以与技术修复同步开展；它是正式分发的重要前提，不能等所有功能做完才处理。安全说明的实际对外发布、代码发布及其他公开写入均需维护者执行或另行明确授权，本次只提供本地分析材料。

如果只投入一个维护周期，优先交付“已知严重问题说明与修复、可重复构建和结果断言、标准密钥及互通示例”三个成果。增加 Web 控制台、Spring Boot starter、完整证书系统、硬件密码机适配或性能优化，均应晚于这些基础能力。项目在稳定前不宜扩大为通用密码平台。

### 衡量是否给使用者带来价值

建议记录首次接入是否能按文档独立完成、主要互通场景是否双向通过、升级是否保住历史数据、依赖冲突能否按文档解决，以及 issue 是否有可复现输入和明确结论。Stars 与下载量可作背景信息，不能代替正确性和维护质量。

对个人项目，持续承诺应控制在能兑现的范围：写明支持版本、维护状态、安全问题入口和不覆盖的场景。如果无法继续提供可靠密码组件维护，明确转为教学仓库、停止引导生产接入，并提供向成熟实现迁移的说明，也是在给开源使用者提供价值。

## 验证材料与复现范围

本目录附有 `LegacyProbe.java`、`ReferenceProbe.java`、`run-probes.sh` 和 `evidence/`。两个 BC 版本在独立 JVM 中运行，避免同名类互相遮蔽。探针只使用合成密钥和消息，输出是否恢复成功，不输出恢复的私钥。

主要环境为 macOS arm64、Maven 3.8.4、Oracle JDK 8u461 和 JDK 17.0.16；独立参考为 `bcprov-jdk18on:1.86`。原依赖为 `bcprov-jdk16:1.46`。运行方法见脚本顶部说明；依赖 jar 不随报告提交。 构建日志中的本机绝对路径已归一化为 `<repo>` 与 `<maven-cache>`，并清理了行尾空白。

| 验证项 | 实际结果 |
| --- | --- |
| 单份固定 nonce 签名恢复合成私钥 | 成功 |
| 签名写出私钥至 stdout | 确认 |
| 相同消息产生相同旧签名 | 确认 |
| 原有效签名中的 s+n 被接受 | 确认 |
| 合法高位私钥签名 | 失败，负数乘法异常 |
| 修改 C3 后解密 | 被接受 |
